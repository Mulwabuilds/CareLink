# CareLink Database Design

## 1. Introduction

This document describes the conceptual database design for CareLink.

The database stores user accounts, provider and patient information, medical records, health updates, recovery information, appointments, messages, and notifications.

The actual database schema is implemented through Django models and migrations.

---

# 2. Database Objectives

The database is designed to:

- Store healthcare information in a structured manner.
- Maintain relationships between providers and patients.
- Preserve medical-record history.
- Support health and recovery monitoring.
- Support appointments and communication.
- Maintain data integrity.
- Enforce appropriate relationships between entities.

---

# 3. Core Entities

## 3.1 User

Represents an authenticated CareLink user.

Possible information includes:

- User ID
- Email
- Password hash
- Role
- Account status
- Date created

---

## 3.2 Provider

Represents a healthcare provider.

Possible information includes:

- Provider ID
- User reference
- Name
- Professional information
- Contact information
- Specialization

---

## 3.3 Patient

Represents a patient.

Possible information includes:

- Patient ID
- User reference
- Name
- Date of birth
- Contact information
- Profile information

Only information required by the system should be collected.

---

## 3.4 Provider–Patient Relationship

Represents an authorized relationship between a provider and a patient.

Possible information includes:

- Relationship ID
- Provider ID
- Patient ID
- Relationship status
- Date assigned

---

## 3.5 Medical Record

Represents a medical record associated with a patient.

Possible information includes:

- Record ID
- Patient ID
- Provider ID
- Record type
- Diagnosis
- Treatment
- Prescription
- Notes
- Creation date

---

## 3.6 Health Update

Represents a health update submitted by a patient.

Possible information includes:

- Update ID
- Patient ID
- Symptoms
- Notes
- Submission date

---

## 3.7 Recovery Update

Represents a recovery-progress update.

Possible information includes:

- Recovery update ID
- Patient ID
- Progress status
- Symptoms
- Notes
- Submission date

---

## 3.8 Appointment

Represents an appointment between a provider and patient.

Possible information includes:

- Appointment ID
- Provider ID
- Patient ID
- Date
- Time
- Status
- Notes

---

## 3.9 Message

Represents communication between users.

Possible information includes:

- Message ID
- Sender
- Recipient
- Message content
- Sent time
- Read status

---

## 3.10 Notification

Represents a notification generated by the system.

Possible information includes:

- Notification ID
- Recipient
- Notification type
- Message
- Read status
- Creation time

---
